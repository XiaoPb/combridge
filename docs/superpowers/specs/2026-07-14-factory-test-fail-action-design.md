# 产测失败动作设计

## 目标

让产测卡控配置中的 `global.fail_action` 真正控制单个测试项阈值失败后的流程，同时保证失败时仍能清理设备、保存部分结果并立即展示失败原因。

## 行为约定

- `enabled: false` 的测试项不执行配置下载、设备命令或数据采集，并在判断结果中记录为未启用。
- 测试项采集完成后立即执行该项阈值判断并发布单项结果。
- `fail_action: stop` 在当前项阈值失败后跳过后续业务测试，但始终执行清理、错误码生成、CSV 保存和最终结果发布。
- `fail_action: continue` 记录当前项失败并继续执行后续启用项，最终总体结果仍为 `FAIL`。
- 配置加载、通信或 RPC 异常不受 `fail_action` 控制，立即终止业务测试，执行清理并返回具体错误原因。
- `LPLCTR` 未启用时不进入环境切换等待。

## 架构

阈值模块提供单项判断函数，产测执行器负责在每项采集后调用它并维护累计判断结果。流程结束路径统一进入收尾阶段，收尾阶段根据已完成的项目生成错误码、保存部分或完整结果，并发布可被前端拉取的最终状态。

前端继续消费现有进度事件，但在 `completed` 和 `failed` 两种终态都拉取产测结果和卡控判断结果。进度事件携带真实的 `step_result`，用于实时记录各步骤结果。

## 状态语义

- `Completed`：所有计划内业务步骤均完成；总体结果可以是 `PASS` 或 `FAIL`。
- `Failed`：因 `stop` 策略或执行异常提前结束；仍存在可展示、可保存的最终结果。
- `Stopped`：操作员主动停止，不承诺生成完整结果。

## 测试

- 单项阈值判断正确复用通道规则。
- `stop`、`continue` 对阈值失败产生不同流程决策。
- 禁用项被标记但不进入执行步骤。
- 执行异常优先于配置策略并保留错误原因。
- 失败终态的前端状态会拉取并保存最终结果。
